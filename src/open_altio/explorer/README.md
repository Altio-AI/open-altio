# Explorer

A release in the browser: filters with case counts and a case list, one case, a product's pages, the filtered export, the Tables and SQL page with read-only SQL. Every query runs on the release's `explorer.duckdb`, through DuckDB held to the memory limit in `rules/explorer-read-memory.md`. The page (`ui/index.html`) draws every screen from the `/api` answers; no page is rendered on the server. The Python modules are listed in `__init__.py`.

```python
from open_altio.explorer.app import create_app

app = create_app("releases/2026Q2")  # one person on this machine (LocalAccess)
app = create_app("releases/live", access=hosted)  # a host decides who views and what
host(host_app, app)  # the host's own routes first, the explorer behind them (RESERVED its own)
```

`release_dir` is a release folder, or a pointer: a small file naming a release folder beside it. `release.point_live` repoints it in one rename and the next request opens the release it names, so a rebuild or a publish switches the explorer without a restart, a symbolic link or replacing a file the explorer holds open. `release.LiveRelease` is the one reader of where the live release is; SQL and the licensed MedDRA part ask it. A licensed MedDRA part an older version added, without the terms report and the text to PT tables, is not served: Home and `open-altio doctor` say so, and `open-altio serve --meddra <folder>` writes it again.

The access hook (`access.py`) is the one question the explorer asks about people: who is viewing, and may they see MedDRA's licensed part, WHO's drug classes (on the pages, and in files: SQL, the Tables page and exports, two answers so a host can give one without the other), SQL and exports. What a reaction is lives in `reactions.py`: where the release holds MedDRA, a viewer counts and finds reactions by their current PT, through the licensed text to PT link (`meddra.py`), unless the hook shows them the release as one without MedDRA (`Viewer.todays_names`), with FDA's text, the statistics counted by it and the hook's line that says so (`fda_text_line`); only a viewer allowed MedDRA's licensed part is shown that link, the current PT beside FDA's text in the case list and a case. `LocalAccess` answers one local person who sees everything the release holds, with no sign-in. What the hook hears is a closed list, part of the written contract (`docs/reference/access-hook.md`): the kinds the server announces (`access.RECORDED`), each through `Explorer.announce`, which raises `ContractError` for any other kind or field, and the kinds the page reports to a host's page modules (`access.REPORTED`, the same list as `ui/host.js`). The viewer a hook names also carries its words for why someone who asks for an SMQ is shown none: locally, that the release holds no MedDRA and how to start the explorer with one's own MedDRA files. A host's hook also names its own page modules (`modules`), which `ui/app.js` loads to add the host's screens through `extend()`, and is told each search (its words and how many results it showed), each export started and made, and each SQL query (`record`), which the explorer on its own keeps nowhere. What only the browser sees goes to `report` in `ui/host.js`: each screen and tab opened, each rule read, each search result picked (MedDRA's licensed levels and WHO's classes by their codes) and each time Improve this is opened. It is empty: a host's page module turns it on, and on its own the explorer sends none of it.

The methods page, How we clean FAERS (`/methods`, which `/rules` forwards to; `rules_api.py`, and `ui/rules/` for the page), tells the build as one story (`story.js`): the funnel to the cases you see, the values read one way, and four questions followed to their answer, every number read from the release's `methods.json`, manifest and cards. Each rule lives in the one box of the story where it acts (`homes.js`), opening to its decision, its findings and its foot (`rows.js`); the words of a finding hold no number (`words.js`). Where the access hook allows it (`edits_rules`; LocalAccess does), a person switches rules and sets values there. Their choices are saved as `rules.toml` beside the release, the file `open-altio build` reads too, and Rebuild runs the build in the background (`rebuild.py`, from the FDA files named by `create_app(..., fda_dir=...)` and the other files the release was built with, `inputs=Inputs(...)`, then the labels step again when the release was flagged); the explorer then answers from the new release. Before the first rebuild with someone's rules, the standard build's methods are kept beside the release as `<release>-standard-methods.json`, so the page can show Altio's counts next to the new ones. A host shows the same page read only. WHO's drug classes are a section of their own with one switch, the switch of their step in `rules/steps.yaml`; the page holds nothing of them where the host's viewer may not see the classes (`Viewer.who`, or for a host's own route the `who` it passes to `rules_page`) or the release carries none and was not built with them switched off.

Improve this on a copy run on someone's own machine is `outbox.py` and `ui/outbox.js`: `create_app(..., outbox=Outbox.on_this_machine())`, as `open-altio serve` runs it, keeps each note in the `outbox` folder of Open Altio's data folder, and the page sends it from the browser to Altio's improvements board, then crosses it off; notes that could not go are sent when a page opens or the browser is back online (rule `improve-this`). An explorer without an outbox, such as the hosted service's, takes no notes itself.

A drug's events (`eventlist.py`, `/api/events`) are one row per event the drug's counted cases name under the question, each count of distinct cases: by today's PT where the release holds MedDRA (`Reactions.key_of` reads FDA's text to it), by the quarter and year of the day a case is dated by (rule `received-day`, the day the received window reads too), with its serious, fatal, life-threatening and fatal or life-threatening cases (rule `serious-outcomes`) and its label flag, the flags of every text read to the event resolved together (`labels.event_flags`). A group of reactions counted as one event (`/api/events/group`) has the same figures, worked out by the same code: every case naming any of the group's reactions counts once under one key, so a group of one reaction is that event's row.

Rules it applies: `ebgm`, `prr`, `ror`, `rrr`, `ic` (their presets), `age-bands`, `explorer-lists`, `explorer-label-flags`, `explorer-label-names`, `dedup-default`, `received-day`, `serious-outcomes`, `era-filter`, `export-csv-row-cap`, `filtered-vs-full-export`, `sql-limits`, `sql-result-download`, `meddra-version`, `meddra-terms`, `legacy-term-spelling`, `improve-this`, `statistics-cases`, `trend-rising`.

A drug's statistics at the end of every quarter (`quarterly.py`, `/api/statistics/quarters`) are its statistics read as they stood at each quarter end, for each event of its statistics or one group of reactions counted as one: every case counted and each reaction's cases are running sums of the release's quarter tables (`quarter_strata_T`, `reaction_quarter_strata_T`), the drug's own cases are counted on the explorer's database, and each quarter end is scored under the release's own prior, so the newest is the pair's own statistics. Screens in `open_altio.stats.screen`'s form say at which quarter ends an event was past one of them, each judged whole (`screen.meets`), and since when; `rising` reads one statistic's trend (`open_altio.stats.trend`, rule `trend-rising`, which waits on its evidence notebook). With `by=event` each case is placed by the date the reaction started, every margin counted on the explorer's database (`quarterplace.py`).

An event's facts (`eventfacts.py`, `/api/events/facts`) read the release for a product's events: the older and children shares of the cases giving an age against the product's own (rule `age-groups`), the cases naming a pregnancy term (`pregnancy-cases`), whether a term is a medical event at all (`not-a-medical-event`), whether the label says the event is the condition the product treats (`treated-condition`) and the share whose reported indication is the event (`indication-match`). These rules wait on their evidence notebook. A fact the release cannot give is null with its reason beside it, never 0 or false; the pregnancy, medical event and indication facts come from MedDRA's licensed part, so a viewer without MedDRA is given them null with the access hook's words.

The case list (`caselist.py`, `/api/cases`) lists the cases behind any count: each count of a drug's events, a group of reactions, the Overview and an event's breakdowns carries `cases_query` (`answers.cases_query`), the case list's question for exactly its cases, under the same question, filters and window. An event is named as `event`, read as a drug's events read it; a breakdown's count adds `period`, `field` and `value`, and `breakdowns.case_filter` picks its cases by the reading the line was counted with, so no field is read a second way. Each page says how many cases the question lists (`total`), may keep to the cases whose number starts with some digits (`case_number`), and sorts by any of its orders (`casecolumns.py`); on a product's page, `detail=columns` adds what each case gives about the drug, read from its own records the way the breakdowns read them (`casecolumns.columns`), so an event's cases can show a column for each field.

A counted question (`counted.py`, `/api/count`) counts a question's cases by one field of rule `counted-question`, distinct cases for each value, each value with its `cases_query`: the value is the one its field's filter takes (`filters.CASE_FIELDS`, `filters.OUTCOMES_GIVEN`), so the case list picks its cases through that filter, and a time takes the days of it the question takes in (`explore.days_query`). The answer says the question in plain words as a filtered export's manifest does (`described.py`), with each filter value `filters.left_out` leaves out. Every count it gives is checked by a second count (`recount.py`, the answer's `check`), made apart from the first: `recountquery.py` reads the question again from its query string, not through `filters.py`, and the count runs as one statement over the release's own Parquet tables on a DuckDB connection of its own, never the explorer database, with Label status counted again from the label flags' tables (`recountlabel.py`) and the filters on the drug records and the report from the drug, onset and indication tables (`recountrecords.py`). `recount.READS` lists each parameter it reads; a question naming any other is not counted again, and its check says so and never that the counts agree. A new filter in `filters.py` joins `READS` and the second count in the same change, or `tests/explorer/test_recount.py` fails. The answer's `sql` is that second count as one query (`recount.sql_of`), each value written in as a quoted constant, which runs as it stands in Tables and SQL to the same counts. Tables and SQL holds MedDRA's licensed tables for a viewer who may see them (`SqlDatabase(meddra=version)`, picked for each viewer by `tables.database`); where the query reads them and the viewer may not, `sql` is null and `why` says so.

An event's breakdowns (`breakdowns/`, `/api/breakdowns`) break its cases down one field at a time, in the order of rule `breakdown-lines`: each value's cases and its share among only the reports that give the field, in a window and before it, and how many reports give the field. `periods.py` places each case in the window (the question's own received days, by default the release's newest quarters) or before it, by the day it is dated by (rule `received-day`), never both; `fields.py` reads each field as a case gives it, a blank or Not given never a value (rules `not-given` and `rechallenge-correction`), from the case or from the product's own drug records (`Unit.records`); `__init__.py` counts each value once a case and keeps the counts per release (`Data.remember`); `lines.py` gives each value's share, change, p-value and whether it rose (rules `chance-test` and `breakdown-rose`), and, on each ask, the value each line shows by its field's pick and whether the line is an alarm (rules `breakdown-alarm` and `dose-strength`, the question's `points`, `fall` and `strength`). The cases are those `/api/events` counts for the event under the same settings and filters. Each line names the filter whose values pick its values' cases (`fields.FILTERS`), and Time to onset gives its days in rule `breakdown-lines`' onset bands too, each band a value of the onset filter.

The filters on what the drug records a question counts give, and on the report (`recordfilters.py`): dose, route, dose form, lot, indication, onset, dechallenge, rechallenge, other drugs, report type and other reactions, with their words, FDA's codes and the onset ranges in `recordfields.py`. They read the product's own records in the roles it is counted in (`drugs.Unit.records`), or every record where a question names no product, a field FDA writes once a record from the first record giving it, by role and then by FDA's drug sequence; `explore.Scope.where` adds them, as it adds the product and the reactions. The breakdowns read each field through the same SQL, so a line's value and its filter pick the same cases. Pregnancy reads MedDRA's licensed part, and Literature waits on FDA's literature reference in the explorer's case table: each is Not available, with the reason, where it cannot be given. These rules wait on their evidence notebook.

## The page

`ui/` holds the page's script as small ES modules, loaded with `<script type="module">`, with no framework and no build step. `app.js` loads them, starts the page and is what a host's page modules import. Its export list, the keys `extend()` takes (`EXTEND_KEYS`) and the places a host draws in (`SLOTS`, both in `host.js`) are closed lists, part of the written contract (`docs/reference/page-extension.md`): an unknown key or place throws, and a new one joins its list and that page in the same change. A person's view choices (the side panel's fold) are read and kept through `viewChoice` and `keepView` in `state.js`, in this browser or where a host's `kept` keeps them. Each part names what its controls do by their `data-act` (`actions` in `events.js`), and one listener hands each click to its part.

How the page looks is checked by screenshots before and after a change (`scripts/screens.py`), and what it does by tests in a browser (`tests/explorer/test_page.py`).

The label flags (`labels.py`) are read from six release tables, `label_flags_T`, `drug_rxnorm_T`, `drug_route_T`, `drug_substance_T`, `ingredient_rxnorm_T` and `label_candidates_T`, which names each label read (`labelnames.py`, rule `explorer-label-names`), when the release holds all but `drug_route_T`, whose absence leaves every record's form unknown, and `ingredient_rxnorm_T`, whose absence reads every page by each record's own code. A page counting any product containing an ingredient reads its records on the ingredient's own label, by the ingredient's own code; one counting the product alone reads them by their own codes (rule `explorer-label-flags`): `/api/labels/product` (a product's reactions), `/api/labels/cases` (Label status's counts), `/api/labels/query` (a group of reactions against the label, with how many were never reported with the drug) and `/api/labels/case/{era}/{key}` (one case). A release without them answers `{}` and the page shows no flags.

A new filter: a field in `filters.py` (read from the query string, written back to it, turned into SQL and into plain words), then its control in `ui/filters.js` and `ui/filtermenu.js`; a filter on the drug records or the report has its SQL in `recordfilters.py`, its words in `recordfields.py`, and its second count in `recountrecords.py`. A new search: a function in `search.py` and its route in `api.py`.

The published questions (`questions.py`) are part of Open Altio's written contract (`docs/reference/api.md`): `PUBLISHED` maps each published route to the function of (Data, Query) that answers it, `INTERNAL` lists the explorer's own routes, and `open_release_data(folder, viewer)` and `ask(route, data, query)` let a product ask the same questions in its own process, of any finished release folder. Every answer that is a JSON object names the release it was counted on (`counted_on`, `answers.py`). A new route is published or internal in the same change: add it to `questions.py`, to the asked questions in `open_altio.testing.contract`, and to `api.md`, then write the snapshot again with `scripts/contract_snapshot.py`.
