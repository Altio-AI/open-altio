# Explorer

A release in the browser: filters with case counts and a case list, one case, a product's pages, the filtered export, the Tables and SQL page with read-only SQL. Every query runs on the release's `explorer.duckdb`, through DuckDB held to the memory limit in `rules/explorer-read-memory.md`. The page (`ui/index.html`) draws every screen from the `/api` answers; no page is rendered on the server. The Python modules are listed in `__init__.py`.

```python
from open_altio.explorer.app import create_app

app = create_app("releases/2026Q2")  # one person on this machine (LocalAccess)
app = create_app("releases/live", access=hosted)  # a host decides who views and what
```

`release_dir` is a release folder, or a pointer: a small file naming a release folder beside it. `release.point_live` repoints it in one rename and the next request opens the release it names, so a rebuild or a publish switches the explorer without a restart, a symbolic link or replacing a file the explorer holds open. `release.LiveRelease` is the one reader of where the live release is; SQL and the licensed MedDRA part ask it. A licensed MedDRA part an older version added, without the terms report and the text to PT tables, is not served: Home and `open-altio doctor` say so, and `open-altio serve --meddra <folder>` writes it again.

The access hook (`access.py`) is the one question the explorer asks about people: who is viewing, and may they see MedDRA's licensed part, WHO's drug classes (on the pages, and in files: SQL, the Tables page and exports, two answers so a host can give one without the other), SQL and exports. What a reaction is lives in `reactions.py`: where the release holds MedDRA, a viewer counts and finds reactions by their current PT, through the licensed text to PT link (`meddra.py`), unless the hook shows them the release as one without MedDRA (`Viewer.todays_names`), with FDA's text, the statistics counted by it and the hook's line that says so (`fda_text_line`); only a viewer allowed MedDRA's licensed part is shown that link, the current PT beside FDA's text in the case list and a case. `LocalAccess` answers one local person who sees everything the release holds, with no sign-in. The viewer a hook names also carries its words for why someone who asks for an SMQ is shown none: locally, that the release holds no MedDRA and how to start the explorer with one's own MedDRA files. A host's hook also names its own page modules (`modules`), which `ui/app.js` loads to add the host's screens through `extend()`, and is told each search (its words and how many results it showed), each export started and made, and each SQL query (`record`), which the explorer on its own keeps nowhere. What only the browser sees goes to `report` in `ui/host.js`: each screen and tab opened, each rule read, each search result picked (MedDRA's licensed levels and WHO's classes by their codes) and each time Improve this is opened. It is empty: a host's page module turns it on, and on its own the explorer sends none of it.

The methods page, How we clean FAERS (`/methods`, which `/rules` forwards to; `rules_api.py`, and `ui/rules/` for the page), tells the build as one story (`story.js`): the funnel to the cases you see, the values read one way, and four questions followed to their answer, every number read from the release's `methods.json`, manifest and cards. Each rule lives in the one box of the story where it acts (`homes.js`), opening to its decision, its findings and its foot (`rows.js`); the words of a finding hold no number (`words.js`). Where the access hook allows it (`edits_rules`; LocalAccess does), a person switches rules and sets values there. Their choices are saved as `rules.toml` beside the release, the file `open-altio build` reads too, and Rebuild runs the build in the background (`rebuild.py`, from the FDA files named by `create_app(..., fda_dir=...)` and the other files the release was built with, `inputs=Inputs(...)`, then the labels step again when the release was flagged); the explorer then answers from the new release. Before the first rebuild with someone's rules, the standard build's methods are kept beside the release as `<release>-standard-methods.json`, so the page can show Altio's counts next to the new ones. A host shows the same page read only. WHO's drug classes are a section of their own with one switch, the switch of their step in `rules/steps.yaml`; the page holds nothing of them where the host's viewer may not see the classes (`Viewer.who`, or for a host's own route the `who` it passes to `rules_page`) or the release carries none and was not built with them switched off.

Improve this on a copy run on someone's own machine is `outbox.py` and `ui/outbox.js`: `create_app(..., outbox=Outbox.on_this_machine())`, as `open-altio serve` runs it, keeps each note in the `outbox` folder of Open Altio's data folder, and the page sends it from the browser to Altio's improvements board, then crosses it off; notes that could not go are sent when a page opens or the browser is back online (rule `improve-this`). An explorer without an outbox, such as the hosted service's, takes no notes itself.

Rules it applies: `ebgm`, `prr`, `ror`, `rrr`, `ic` (their presets), `age-bands`, `explorer-lists`, `explorer-label-flags`, `explorer-label-names`, `dedup-default`, `era-filter`, `export-csv-row-cap`, `filtered-vs-full-export`, `sql-limits`, `sql-result-download`, `meddra-version`, `meddra-terms`, `legacy-term-spelling`, `improve-this`.

## The page

`ui/` holds the page's script as small ES modules, loaded with `<script type="module">`, with no framework and no build step. `app.js` loads them, starts the page and is what a host's page modules import. Each part names what its controls do by their `data-act` (`actions` in `events.js`), and one listener hands each click to its part.

| Module | What it is |
|---|---|
| `util.js`, `codes.js`, `countries.js`, `icons.js` | Escaping, numbers and dates as a person reads them, and the link to a value's rule; FDA's codes in words; countries by name, with rule legacy-country's notes; the icons |
| `state.js`, `server.js` | What the page knows (`S`, this browser's kept choices, each scope's filters); `/api` answers |
| `events.js`, `overlays.js`, `host.js` | What clicks do; dialogs, menus, toasts and tips; what a host's page modules add (`extend`) |
| `router.js`, `frame.js`, `products.js` | Addresses and drawing a page; the side panel and its rail, and the line saying how current the data is; pinning a product, and the pinned ones in the side panel |
| `home.js`, `scope.js`, `charts.js`, `cases.js`, `casedialog.js`, `meddra.js` | Home; a product's page or All cases; its Overview, its Cases and one case; a MedDRA term FDA wrote, with its spelling and, where MedDRA may be seen, its current PT |
| `statistics.js`, `screens.js` | The Statistics tab; the screens it reads its pairs with, and their menu |
| `classstats.js` | The Statistics tab by WHO class: All cases' list by class at one level, and a drug's class's EB05 beside its own |
| `filters.js`, `filtermenu.js`, `terms.js`, `cmq.js`, `queries.js` | The filters in words and as a query; the filters menu; the Reactions search; a person's own queries, and where they are kept (this browser, or a host's account where a group shares them) |
| `drugs.js`, `classes.js` | How a drug counts, and the Drugs and Spellings filters; WHO's drug classes: the Drug class filter and each drug's class |
| `labels.js`, `labelstats.js` | The label flags: each in words with its tip, Label status's pane, the lines in the case dialog, About the label flags; Statistics' Label column and its filters |
| `tables.js`, `tablewords.js`, `sql.js`, `downloads.js`, `exports.js` | Tables and SQL; the release's tables in words; SQL; downloads; the filtered export |
| `settings.js`, `improve.js`, `outbox.js` | Settings; Improve this, where a host takes notes; on a copy with an outbox, the email, the offline line and the sending to Altio |

How the page looks is checked by screenshots before and after a change (`scripts/screens.py`), and what it does by tests in a browser (`tests/explorer/test_page.py`).

The label flags (`labels.py`) are read from six release tables, `label_flags_T`, `drug_rxnorm_T`, `drug_route_T`, `drug_substance_T`, `ingredient_rxnorm_T` and `label_candidates_T`, which names each label read (`labelnames.py`, rule `explorer-label-names`), when the release holds all but `drug_route_T`, whose absence leaves every record's form unknown, and `ingredient_rxnorm_T`, whose absence reads every page by each record's own code. A page counting any product containing an ingredient reads its records on the ingredient's own label, by the ingredient's own code; one counting the product alone reads them by their own codes (rule `explorer-label-flags`): `/api/labels/product` (a product's reactions), `/api/labels/cases` (Label status's counts) and `/api/labels/case/{era}/{key}` (one case). A release without them answers `{}` and the page shows no flags.

A new filter: a field in `filters.py` (read from the query string, written back to it, turned into SQL and into plain words), then its control in `ui/filters.js` and `ui/filtermenu.js`. A new search: a function in `search.py` and its route in `api.py`.
